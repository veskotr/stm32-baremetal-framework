# Config System Roadmap

The HSS config system should provide a small, readable way for applications to declare framework and product options without scattering compile definitions through CMake files and source code.

The first version should stay intentionally simple. It should solve common embedded configuration needs, generate C and CMake values, support profile-specific overrides from day one, and avoid becoming a full menuconfig clone before the framework has enough real projects to justify that complexity.

## Goals

- keep project options centralized and easy to review
- generate a C header that application and framework code can include
- optionally expose the same values to CMake
- support app-owned configuration files outside the framework repository
- support named profiles such as `dev`, `release`, `test`, and hardware revisions
- make the active profile set configurable from CMake
- provide useful validation errors during configure or generation
- keep the input format easy to edit by hand and version control
- preserve the existing CubeMX boundary: CubeMX owns hardware setup, config owns framework/product choices

## Non-goals

- no GUI configurator in the first version
- no interactive terminal configurator in the first version
- no hidden board probing beyond values already generated by board sync
- no replacement for `board_roles.cmake`
- no attempt to configure STM32 HAL peripherals that should stay in CubeMX

## Intended Use

An application should be able to add a base config file plus optional profile files next to its `CMakeLists.txt`:

```text
my_app/
  CMakeLists.txt
  hss.conf
  hss-dev.conf
  hss-release.conf
  hss-test.conf
  hss-hw_rev_b.conf
  boards/
  src/
```

Example first-pass config:

```text
# Feature flags
HSS_ENABLE_FREEMODBUS=y
HSS_ENABLE_MODBUS_DEBUG=n

# Console behavior
HSS_CONSOLE_STDIO_TIMEOUT_MS=1000

# Product/application values
APP_DEVICE_NAME="temp-transmitter"
APP_SAMPLE_PERIOD_MS=1000
```

Example `hss-dev.conf`:

```text
HSS_ENABLE_MODBUS_DEBUG=y
HSS_CONSOLE_STDIO_TIMEOUT_MS=3000
APP_SAMPLE_PERIOD_MS=250
```

Example `hss-release.conf`:

```text
HSS_ENABLE_MODBUS_DEBUG=n
APP_SAMPLE_PERIOD_MS=1000
```

Example `hss-hw_rev_b.conf`:

```text
APP_BOARD_REVISION="B"
APP_SENSOR_CS_ACTIVE_LOW=y
```

Application CMake should stay small:

```cmake
hss_add_firmware(my_app
        BOARD my_board
        CONFIG hss.conf
        PROFILES dev
        src/main.c
)
```

Profiles should also be selectable from the configure command:

```sh
cmake -S . -B build/dev -DHSS_CONFIG_PROFILES=dev
cmake -S . -B build/release -DHSS_CONFIG_PROFILES=release
cmake -S . -B build/rev_b -DHSS_CONFIG_PROFILES=release\;hw_rev_b
cmake -S . -B build/local -DHSS_CONFIG_PROFILES=release\;local -DHSS_CONFIG_OPTIONAL_PROFILES=local
```

The generated C header should be included as:

```c
#include "hss_config.h"
```

Generated C values should look like:

```c
#define HSS_ENABLE_FREEMODBUS 1
#define HSS_ENABLE_MODBUS_DEBUG 0
#define HSS_CONSOLE_STDIO_TIMEOUT_MS 1000
#define CONFIG_APP_DEVICE_NAME "temp-transmitter"
#define CONFIG_APP_SAMPLE_PERIOD_MS 1000
#define HSS_CONFIG_ACTIVE_PROFILES "release;hw_rev_b"
```

## Input Format

The preferred first format is a simple line-oriented `KEY=VALUE` file. The profile behavior should feel similar to Spring Boot profiles, but without requiring YAML/TOML dependencies in the first implementation.

Rules:

- blank lines are ignored
- lines that start with `#` are comments
- `#` also starts a trailing comment outside quoted strings
- keys must use `A-Z0-9_`
- booleans accept `y/n`, `yes/no`, `true/false`, and `on/off`
- integers are decimal first; hexadecimal can be added if needed
- quoted strings use double quotes
- unquoted strings are allowed only if they contain simple identifier/path characters
- non-empty lines that cannot be parsed are logged as warnings and ignored

This keeps the parser small and avoids adding YAML/TOML dependencies.

## Profile Model

Profiles are ordered overlays on top of a base config.

Default merge order:

1. `hss.conf`
2. `hss-<profile1>.conf`
3. `hss-<profile2>.conf`
4. later profiles override earlier profiles

Example:

```sh
-DHSS_CONFIG_PROFILES=release\;hw_rev_b
```

Loads:

```text
hss.conf
hss-release.conf
hss-hw_rev_b.conf
```

If the same key exists in multiple files, the last loaded value wins. The generator should record where the final value came from so diagnostics can explain overrides.

Profile names:

- should use lowercase letters, numbers, and underscores
- should be stable names such as `dev`, `release`, `test`, `factory`, `hw_rev_a`, `hw_rev_b`
- should be independent of CMake build type, although projects may choose matching names

Missing profile files are configurable:

- default behavior: error when an explicitly selected profile file is missing
- profiles listed in `HSS_CONFIG_OPTIONAL_PROFILES` or `OPTIONAL_PROFILES` warn and continue when missing

Explicit profile files are also supported for overlays that do not follow the
`hss-<profile>.conf` naming convention:

```cmake
hss_add_firmware(my_app
        BOARD my_board
        CONFIG hss.conf
        PROFILES release
        PROFILE_FILES boards/rev_b.conf
        src/main.c
)
```

The active profile list should be available in generated C and CMake output:

```c
#define HSS_CONFIG_ACTIVE_PROFILES "release;hw_rev_b"
#define HSS_CONFIG_PROFILE_RELEASE 1
#define HSS_CONFIG_PROFILE_HW_REV_B 1
```

The base `hss.conf` always loads first. A firmware target can override the base filename, but the default prefix is `hss`.

## Validation Model

The config system should have two layers:

- a schema that defines known framework options
- a generated output step that preserves app-owned custom values

Framework options with the `HSS_` prefix should be validated strictly when they are known. Application-specific custom properties should be allowed too.

Only C-facing values are emitted to `hss_config.h`:

- known `HSS_` framework keys
- custom `APP_` keys, emitted as `CONFIG_APP_<NAME>`
- custom keys that already start with `CONFIG_`

Other parsed custom keys remain available in `hss_config.cmake` and `hss_config.meta`, but they are not emitted to the C header. This keeps tool/build-only settings out of firmware code while still preserving them for CMake and diagnostics.

Initial framework keys:

- `HSS_ENABLE_FREEMODBUS`
- `HSS_ENABLE_MAX31865`
- `HSS_ENABLE_MODBUS_DEBUG`
- `HSS_CONSOLE_STDIO_TIMEOUT_MS`

Candidate future keys:

- default UART/SPI/timer operation timeouts
- feature toggles for optional drivers
- protocol defaults such as Modbus baud-rate assumptions or register-bank sizes, where those are not CubeMX-owned
- test/host-mode feature toggles

## Generated Outputs

For each firmware target using config, generate:

```text
<build>/hss_generated/<target>/hss_config.h
<build>/hss_generated/<target>/hss_config.cmake
<build>/hss_generated/<target>/hss_config.meta
```

`hss_config.h` is consumed by C code.

`hss_config.cmake` can be included by the framework during configure so options that affect target composition are available to CMake.

`hss_config.meta` can record the loaded files, active profiles, final values, and source locations for diagnostics. The exact format can be simple text or JSON.

Values that affect which optional framework targets are built, such as `HSS_ENABLE_FREEMODBUS`, are parsed during `hss_add_firmware()`. The framework may then enable the requested optional module for that target. Existing CMake cache options remain supported as compatibility fallbacks when no config file is provided.

## CMake API Roadmap

First API:

```cmake
hss_add_firmware(my_app
        BOARD my_board
        CONFIG hss.conf
        PROFILES dev
        src/main.c
)
```

Configure-time profile selection:

```cmake
set(HSS_CONFIG_PROFILES "dev" CACHE STRING "Active HSS config profiles")
set(HSS_CONFIG_OPTIONAL_PROFILES "local" CACHE STRING "Optional HSS config profiles")
set(HSS_CONFIG_PROFILE_FILES "boards/rev_b.conf" CACHE STRING "Additional HSS config profile files")
```

or:

```sh
cmake -S . -B build/dev -DHSS_CONFIG_PROFILES=dev
```

Possible supporting APIs:

```cmake
hss_generate_config(my_app CONFIG hss.conf PROFILES dev)
hss_target_config(my_app CONFIG hss.conf PROFILES release PROFILE_FILES boards/rev_b.conf)
```

Design preference:

- make `CONFIG` on `hss_add_firmware()` the normal user path
- support `PROFILES` on `hss_add_firmware()` for target-local explicit profiles
- use `HSS_CONFIG_PROFILES` as the build-directory default when `PROFILES` is omitted
- support `OPTIONAL_PROFILES` / `HSS_CONFIG_OPTIONAL_PROFILES` for machine-local overlays
- support `PROFILE_FILES` / `HSS_CONFIG_PROFILE_FILES` for explicit overlay paths
- keep helper functions internal until real examples need them
- generated include dirs should be target-specific
- config should not silently affect unrelated firmware targets in the same build

## Implementation Phases

Current status:

- Phases 1-4 have a first implementation.
- Phase 5 has focused parser/generator tests and a CMake build smoke test for the Blue Pill Modbus slave example.
- Phase 6 remains future refinement for items such as richer config merging and optional future YAML support.

### Phase 1: design and docs

- create this roadmap
- refine supported input types and validation rules
- keep existing CMake cache options as compatibility fallbacks
- document how apps should name product-specific keys
- define profile merge order and missing-profile behavior

### Phase 2: parser and generator

- add `tools/config/` Python package split into parser/model/rendering modules
- add `tools/generate_config.py` command wrapper
- parse base `KEY=VALUE` files
- parse profile override files such as `hss-dev.conf`
- merge configs in deterministic profile order
- normalize booleans, integers, and strings
- generate `hss_config.h`
- generate `hss_config.cmake`
- generate profile metadata
- write files only when content changes
- add useful errors and warnings with filename and line number

### Phase 3: CMake integration

- add `CONFIG <file>` support to `hss_add_firmware()`
- add `PROFILES <profiles...>` support to `hss_add_firmware()`
- add `OPTIONAL_PROFILES <profiles...>` support to `hss_add_firmware()`
- add `PROFILE_FILES <files...>` support to `hss_add_firmware()`
- add `HSS_CONFIG_PROFILES` cache variable for build-directory profile selection
- add `HSS_CONFIG_OPTIONAL_PROFILES` and `HSS_CONFIG_PROFILE_FILES` cache variables
- generate config during configure
- add generated include directory to the firmware target
- expose generated CMake values for target-local framework decisions
- keep existing CMake cache options as compatibility fallbacks when no config file is provided

### Phase 4: examples

- add config to one minimal example
- add config to the Blue Pill Modbus slave example
- add at least `dev` and `release` profiles to one example
- add a hardware revision profile overlay example
- document external project usage
- show the generated `hss_config.h` include path and example usage

### Phase 5: tests

- add host-side parser tests
- add generator golden-output tests
- add profile merge-order tests
- add missing-profile error tests
- add CMake configure/build smoke coverage for an example using config

### Phase 6: refinement

- add schema metadata if needed: type, default, allowed range, documentation string
- add optional default config fragments
- add richer config merging if real apps need shared fragments beyond profiles
- consider YAML support only if the line-oriented profile model becomes limiting
- consider a future interactive editor only after the file format stabilizes

## Open Questions

1. Should optional profile warnings be suppressible for expected local-only profiles?
2. Which additional framework feature flags should move into config after `HSS_ENABLE_FREEMODBUS` and `HSS_ENABLE_MAX31865`?
3. Should config support explicit custom-key allow-lists later, or is automatic `CONFIG_` prefixing enough?
4. Should there be a future syntax or schema field for forcing a custom key into or out of `hss_config.h`?
5. Should board-specific defaults be allowed later, or should board roles and app config remain completely separate?
6. Should missing selected profile files always be fatal, or should CMake support optional profiles?

## Recommended First Cut

Build the smallest useful version:

- one base config file per firmware target
- ordered profile overlays from day one, including optional profiles and explicit profile files
- active profiles configured through `HSS_CONFIG_PROFILES` or `hss_add_firmware(... PROFILES ...)`
- strict validation for known `HSS_` keys
- emit only C-facing values to `hss_config.h`: known `HSS_`, `APP_`, and `CONFIG_` keys
- generate `hss_config.h`
- generate `hss_config.cmake`
- generate profile metadata
- integrate through `hss_add_firmware(... CONFIG hss.conf PROFILES dev ...)`
- keep existing CMake cache options working when no config file is provided

This gives the framework a clear configuration path without locking it into a large configuration system too early.
