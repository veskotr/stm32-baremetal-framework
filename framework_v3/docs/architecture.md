# framework_v3 Architecture

## Purpose

`framework_v3` exists to make STM32 projects easier to start, extend, and reuse.

It should provide:
- a stable project structure
- a simple STM32 HAL-oriented programming model
- reusable framework code for common integrations
- automation around board metadata and generated code
- a smooth build / flash / debug workflow
- project configuration similar in spirit to ESP-IDF, but much simpler

It should not provide:
- a fake cross-vendor hardware abstraction
- a complicated portability layer that hides HAL
- a framework that fights CubeMX

## Core Principles

1. STM32-only

The framework targets STM32 MCUs that use the HAL. Portability across STM32 families is valuable. Portability outside STM32 is not a goal.

2. HAL-first, not HAL-free

HAL types and concepts are allowed to appear in framework code where doing so keeps the code simpler and more maintainable.

3. CubeMX owns generated board code

CubeMX remains the source of truth for:
- clocks
- pinmux
- peripheral init
- startup files
- linker scripts
- HAL configuration
- generated interrupt and MSP code

4. Framework code reduces repetition

The framework should remove boilerplate, standardize common patterns, and make reuse easier. It should not over-abstract hardware details just for architectural purity.

5. Automation over tribal knowledge

If a new board or feature requires repeated manual steps, those steps should be moved into scripts, generators, or documented conventions.

6. Stable workflow matters

The developer experience should always support:
- build
- flash
- debug
- inspect firmware size and memory usage
- configure project options

7. The framework owns the build system

CubeMX is used to generate board source assets. `framework_v3` owns the build, flash, debug, configuration, and reporting workflow.

## Layering

The intended layering is:

1. CubeMX board output
2. board integration files
3. HAL helper layer
4. reusable protocol and driver integration layers
5. application code

### 1. CubeMX board output

This is the board-specific generated code and assets:
- `.ioc`
- `Core/`
- `Drivers/`
- startup files
- linker script

This layer is regenerated by CubeMX and should be treated as generated source.

CubeMX may also be able to generate build files, but those are not intended to be the primary build path for this framework.

### 2. Board integration files

Each board should have a small amount of framework-owned metadata that describes:
- MCU family and board identity
- which peripherals are used
- which peripherals are assigned to framework roles
- pins assigned to named roles
- OpenOCD settings
- flash and RAM sizes

This layer bridges CubeMX output into the framework.

Examples of semantic roles:
- Modbus UART
- Modbus timer
- Modbus RS-485 DE pin
- SPI bus for a sensor
- chip-select pin
- status LED

### 3. HAL helper layer

This layer provides thin helpers around repeated HAL usage.

It should stay simple and direct. It is acceptable for it to expose or consume HAL handles such as:
- `UART_HandleTypeDef *`
- `SPI_HandleTypeDef *`
- `TIM_HandleTypeDef *`
- `GPIO_TypeDef *`

The point of this layer is consistency and reuse, not total abstraction.

### 4. Reusable protocol and driver integration layers

This layer contains reusable integrations such as:
- FreeModbus STM32 port
- Analog Devices no-OS STM32 port
- future reusable driver bindings

These integrations should rely on framework-owned board metadata and helpers rather than per-project handwritten boilerplate.

### 5. Application code

Application code should focus on:
- product behavior
- protocol configuration
- register maps
- business logic
- sensor behavior
- state machines

Application code should not be responsible for recreating framework setup for each project.

## Planned Folder Structure

The exact contents may evolve, but the intended structure is:

- `framework_v3/boards`
- `framework_v3/cmake`
- `framework_v3/hal`
- `framework_v3/protocols`
- `framework_v3/drivers`
- `framework_v3/tools`
- `framework_v3/docs`
- `framework_v3/examples`

### boards

Holds board-specific integration and metadata.

Expected contents per board may include:
- CubeMX project files
- framework board manifest
- generated capability headers
- semantic role mapping
- OpenOCD configuration metadata

Framework-owned board files should also contain the CMake logic needed to build the CubeMX-generated sources for that board.

### cmake

Holds reusable CMake functions for:
- board selection
- firmware target creation
- generated config integration
- flash targets
- debug targets
- post-build reporting

### hal

Holds thin STM32 HAL-oriented helpers and reusable wrappers.

Expected focus areas:
- UART
- SPI
- GPIO
- timer
- delay/time
- critical section helpers

### protocols

Holds reusable protocol integrations.

Initial target:
- `freemodbus`

### drivers

Holds reusable driver integrations.

Initial target:
- `adi_no_os`

### tools

Holds scripts and tooling for:
- board metadata generation
- CubeMX sync/patch steps
- config generation
- size/report generation
- OpenOCD helpers
- VS Code integration

### docs

Holds architecture and contributor documentation.

### examples

Holds small firmware projects that demonstrate how external applications consume the framework.

Examples are allowed in the framework repository because they teach and verify the workflow. Production applications should live outside this repository and consume the framework as a submodule or dependency.

## Automation Strategy

Automation is a core part of the framework.

### Board generation and sync

The framework should eventually provide scripts that:
- inspect CubeMX project data
- derive board capabilities
- generate board metadata files
- patch or sync required framework-owned insertions into generated code

The purpose is to avoid requiring developers to memorize setup steps for every new project.

Future project documentation may also define the required CubeMX generation settings and flags so that new board projects are created in a consistent way.

### Project configuration

The framework should eventually provide a simple project config flow inspired by ESP-IDF:
- a user-edited config file
- generated config headers
- optional generated CMake config values

This should stay lightweight and easy to understand.

### Build reporting

Every build should aim to produce:
- `.elf`
- `.bin`
- `.hex`
- `.map`

And report useful stats such as:
- flash usage
- RAM usage
- section sizes
- output artifact locations
- optional largest objects or symbols

## Intended Developer Workflow

The normal workflow should be:

1. select or create a board
2. regenerate CubeMX code if needed
3. run framework sync/generation tools
4. configure project options
5. build firmware
6. flash firmware
7. debug firmware in VS Code

This workflow should be stable across projects.

## Build Ownership

`framework_v3` owns the build system.

That means:
- CubeMX generates board code
- `framework_v3` provides and maintains the CMake files
- `framework_v3` provides flash and debug targets
- `framework_v3` provides post-build reporting

CubeMX-generated `Makefile` or `CMake` output may exist, but it should not be treated as the primary project workflow.

The preferred model is:
- each board keeps its own CubeMX-generated source package
- the framework builds that package through framework-owned CMake
- board sync tooling updates metadata and integration files around it

This keeps the developer workflow stable even when CubeMX generation changes.

## Simplicity Rules

When in doubt:
- choose the simpler API
- prefer explicit role mapping over clever inference
- prefer generation over manual repeated edits
- prefer stable conventions over flexible but confusing systems
- prefer STM32 HAL reality over artificial abstraction

## Documentation Rule

`framework_v3` is expected to grow over time.

Every new framework feature must update the documentation when it changes:
- architecture
- folder layout
- generated files
- required workflow
- conventions for new boards
- rules for new integrations

If code changes the way the framework is meant to be used, the docs must be updated in the same change.

Future documentation should also include a dedicated CubeMX generation guide with the expected project settings, generation options, and regeneration workflow for new boards.
